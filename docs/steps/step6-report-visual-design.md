# Step 6: アラート詳細 AI レポートの視覚再設計（タスク E8・設計）

> **位置づけ**: `step6-final-sprint-strategy.md` §1 の AI 審査員5名レンズで、アラート詳細ページ（`AlertDetailPage` ＋ `AlertCardExpanded` full 射影）を「情報は正しいが読む物」から「一目で構造が分かる報告書」へ格上げする設計。
> **契機**: 実機スクリーンショット（2026-07-04・シナリオ3 在庫引当の失敗）のレビュー。情報粒度・カテゴリ分けは良いが、**全セクションが同じ視覚密度のテキスト縦積み**で、証拠がどこから来て結論にどう収束したかという*構造*が文でしか表現されていない。
> **対応 todo**: `step6-final-sprint-todo.md` タスク E8。**backend 変更ゼロ**（既存 wire データの表示射影のみ）・frontend の domain 純関数＋presentation のみ。

---

## 1. 現状の問題（実スクリーンショットベース）

1. **視覚密度が均一**: AI推定パターン→働きの明細→summary→調査ステップ→推奨アクション→影響評価→算定根拠→収集した証拠→承認、の10ゾーン超が全部「小見出し＋テキスト」の同じ濃度で縦積み。**どこを見ればいいかの答えが画面に無い**（Lisa 直撃）。
2. **調査ステップが箇条書き3行**: 「1. root_cause_analystで根本原因を分析」等の生エージェント名テキスト。**7エージェント自律調査という最大の売りが、成果物側では ol リストに退化**している（E1 でライブ中は可視化済みなのに、完了後の報告書では消える）。
3. **算定根拠（引用）が生ログ monospace チップの横並び**: 正直さの担保として必須だが、`appLogs: message: "Deadlock found..."` が5連続で並ぶと「読ませる気のない密度」になる。消すのではなく畳み方の問題。
4. **証拠の流入構造が見えない**: 「143秒で GitHub・類似事例DB を横断し、証拠15件を収集」は1行テキスト。**どのソースから何件来て、どう1つの結論に収束したか**——このシステムの働きの核心——が図になっていない（ユーザー指摘の本丸）。

## 3. 提案A: 証拠フローダイアグラム 〔P0・本丸・ユーザー案の具体化〕

「どこから証拠が流入し、AI がどう1つの結論に収束させたか」を左→右の3カラム図で描く。**チャートライブラリ不使用**（SVG コネクタ＋flex/grid の手組み・テーマ整合・依存追加なし）。

```
┌─ 証拠の流れ ──────────────────────────────────────────────────┐
│                                                                │
│  ▤ Cloud Logging   4件 ━━━┓                                   │
│                            ┃      ┌──────────────┐             │
│  ❮❯ GitHub         6件 ━━━╋━━━▶ │  AI 調査      │            │
│                            ┃      │  7エージェント │ ━━▶ ◆ 結論 │
│  ◎ 類似事例DB      5件 ━━━┛      │  ⏱ 143秒     │    INVENTORY_ │
│                                   └──────────────┘    CONCURRENT_ │
│  （0件のソースは描かない）                              CONFLICT   │
│                                                        確信度 ▓▓▓░ 70% │
│                                                        自責（自社コード起因） │
└────────────────────────────────────────────────────────────────┘
```

- **左（流入源ノード）**: `metrics.evidenceCounts` の 5 ソース（logs/metrics/terraformChanges/commits/similarIncidents）のうち **>0 のみ**。アイコン・呼称は `investigationProgress.ts` の TOOL_META / `investigationWorkload.ts` の SOURCE_LABELS と統一。
- **コネクタ**: 件数を線の太さ（2段階か3段階の離散で十分・連続スケールは fake precision）で視覚エンコード。
- **中（AI 調査ノード）**: `⏱ {elapsedLabel}`・「7エージェント」。クリック/ホバーは不要（E1 のライブビューが過程を担う。ここは*結果の構造*）。
- **右（結論ノード）**: `suggestedPatternName`＋確信度ゲージ（既存 ConfidenceCalibrationNote をゲージ直下に併置＝キャリブレーション可視化と合流）＋ `impact.fault` バッジ。
- **G1 の ⏱ テキスト1行はこの図に吸収**（同じ数字を二度出さない）。図が描けない条件では現行テキスト1行へ劣化。

**正直さ（David）**: 全て backend 記録済みの実測（`InvestigationMetricsPrimitives`）。LLM 出力に依存しない deterministic 導出（G1 と同じ性質）なので図が嘘をつく経路が無い。

**劣化経路**: `metrics` 無し（旧 Alert）→ 図もテキストも非表示（現行同等）。`isFallback` → 図を出さない（E3 の証拠リンク温存表示が主役）。全ソース0件 → 「調査を実行して原因を推定」の現行文言。

**実装形**: domain 純関数 `evidenceFlowModel(report): EvidenceFlowModel | null`（UT）→ `EvidenceFlowDiagram`（RTL・aria は「証拠の流れ: Cloud Logging 4件…」の読み上げテキストを併記）。

## 4. 提案B: 調査ステップのタイムライン化 〔P0〕

`investigationSteps` の ol リストを、E1 完了タイムラインと同じ意匠の**縦タイムライン**（左に接続線＋ノード・kind アイコン・リンクは既存 InvestigationItem 流用）へ。

```
調査の道筋
 ●─ 🧭 Coordinator      調査全体を指揮し、専門エージェントへ委譲
 │
 ●─ 🔍 RootCauseAnalyst  根本原因を分析
 │
 ●─ ⚖ ImpactTriage      影響を評価
 │
 ●─ 🛠 RemediationPlanner 修正方針を起案
```

- ステップ文中の生エージェント名（`root_cause_analyst` 等）を `INVESTIGATION_AGENTS` の label/role へ**表示時に人間語化**（domain 純関数・一致しなければ原文のまま＝防御的）。E2「生 ID 露出の人間化」と同じ既存方針の適用。
- **所要時刻は出さない**: ステップ毎の実測タイムスタンプは記録していない。順序のみを接続線で表現し、時刻の捏造をしない（F8 でタイムチャートを不採用にしたのと同じ判断）。
- fallback の「収集済みの証拠リンク」（E3）は現行のまま（タイムラインにしない＝調査の道筋ではなく残骸のリンク集）。

## 5. 提案C: 結論ファーストの再配置 〔P0・コード最小〕

full 射影の描画順を「読む順」から「判断する順」へ。新規コンポーネントなしの並べ替え＋ヒーロー化が主。

```
[1] ヒーロー: AI推定パターン ＋ 確信度ゲージ ＋ 自責/他責 ＋ 障害規模1行   ← 5秒で判断材料が揃う
[2] summary（原因の1段落）
[3] 証拠フローダイアグラム（提案A）
[4] 推奨アクション（remediable バッジ含む）                                  ← 「どうする」を根拠の直後へ
[5] 調査の道筋（提案B・タイムライン）
[6] 影響評価の詳細（scope/subjects/算定根拠→提案D）
[7] escalation / remediationReview（該当時のみ・現行どおり）
[8] 関連アラート / 修正提案 / 収集した証拠（ページ側パネル・現行どおり）
[9] 承認/却下（報告書の締め・現行位置を維持）
```

- 現状は「障害規模・fault」が下段の影響評価パネルまで出てこない。**fault バッジと scale はヒーローへ昇格**し、影響評価パネルには詳細（scope・subjects・引用）を残す（重複は fault/scale の2項目のみ・判断速度を買う）。
- summary 射影（ドロワー）は**ノータッチ**（トリアージ用の射影境界＝タスク37 の決定を動かさない）。

## 6. 提案D: 引用チップの可読化 〔P1〕

- 「算定根拠（引用）」「エスカレーション証拠」の生ログチップを**折りたたみ**（`算定根拠 5件 ▸` クリックで展開）＋各チップは1行 trim・展開で全文。
- 展開時はソース種別（appLogs / metrics / occurrenceCount…）の**左ボーダー・レーン**でグルーピング＝F8 の RiskCard 引用レーン（変更予定 cyan／負荷予定 amber／記憶 emerald）と同じ視覚言語をアラート側にも通す。
- 折りたたんでも件数チップは常時見える＝「根拠がある」ことは一目・「根拠を読む」は要求時（段階開示）。

## 7. 提案E: 密度の微調整 〔P1・小粒〕

- セクション間の余白拡大（`space-y-4` → セクション境界は `space-y-6` 相当）と、小見出しの階層強化（現状は全見出しが同じ `text-xs uppercase`）。
- summary 段落へ `max-w-prose`（70字超の行長は可読性を落とす）。
- ヒーロー以外の本文フォントは現行のまま（縮めない・読ませる場所は読める大きさで）。

## 8. やらないこと（検討の上で棄却）

- **チャートライブラリ導入**（Recharts 等）: 依存追加・ダークテーマ整合コスト・この図は SVG 手組みで十分。
- **サンキーダイアグラム本格実装**（曲線束・比例帯）: 5ソース→1結論の単純な収束に対して視覚コスト過剰・fake precision のリスク。直線コネクタ＋離散太さで足りる。
- **ステップ毎の所要時間・タイムスタンプ表示**: 記録が無い＝捏造になる。
- **エージェント関係グラフ（hub-and-spoke 図）のレポート内描画**: E1 の台帳＋ライブ中継が既に担う。完了報告書には*結果の構造*（証拠フロー）だけを置き、役割の重複を作らない。
- **summary 射影（ドロワー）への波及**: 射影境界は動かさない。
