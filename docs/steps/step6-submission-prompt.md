# Step 6: 提出資料作成プロンプト（ブラウザ Claude 用・自己完結）

> **使い方**: スマホのブラウザ Claude に、まず「§A 事実パック」を丸ごと貼って前提を読み込ませ、続けて §B の作りたい資料のプロンプトを1つずつ貼る。**§A に嘘のない事実だけ**を封入してある（ここに無いことは書かせない）。
> **精度を上げる併用（推奨）**: §A と一緒にルートの `README.md` と `docs/architecture.md` の本文も貼る（リポジトリが公開済みなら GitHub の URL を渡して読ませてもよい）。両者は**コードを正**として書かれており、§A の要約より詳細な用語・構成・API 名・Mermaid 図を正確に補完する。§A と食い違ったら README / architecture 側を正とする。
> 成果物: ProtoPedia の各欄（概要・ストーリー・システム構成補足）／動画台本／アーキ図の構成指示／紹介画像5枚の構成案。

## §A 事実パック（最初に貼る・これが唯一の情報源）

```
あなたはハッカソン提出資料のライターです。以下の事実パックだけを情報源とし、
ここに書かれていないことは推測で書かないでください。誇張・盛りは禁止。
「実装済み」と「設計のみ」を混同しないこと。以降の指示で各資料を作ります。

【ハッカソン】
- Findy「DevOps × AI Agent Hackathon 2026」。Google Cloud 主催協賛・賞金総額200万。
- 審査観点（公式）: アイデアの面白さ／エージェントとしての必然性／自律的判断とタスク実行の設計／実運用を見据えたDevOpsプロセス。
- 提出: 公開GitHubリポジトリ／デプロイ済みURL（審査員が実際に触る）／ProtoPedia（動画・アーキ図必須・ストーリー）。

【プロダクト一言】
既存の観測基盤（Cloud Monitoring）の「検知」の上に乗り、アラート発火後の
「調査 → 評価 → レビュー」の人手ワークフローを AI エージェントが圧縮する。
さらに「起きる前」に引用付きでリスクを予報する（予兆ブリーフィング）。

【解決したい課題】
障害対応で最も時間を食うのは検知ではなく、その後の「複数ソースを人手で
横断して原因を調べ、影響を見積もり、報告を書く」作業。既存SaaSは同じ障害が
再発しても毎回ゼロから調べ直す。オンコール担当の MTTR と認知負荷を削る。

【想定ユーザー】
EC等のWebサービスを運用する SRE・オンコールエンジニア・バックオフィス運用者。

【アーキテクチャ（すべて実装済み・テスト694件緑）】
- EC ドメイン（注文・在庫・決済）: TypeScript/Express、DDD+Clean Architecture+CQRS+EDA
  （CodelyTV パターン準拠）。RabbitMQ で DomainEvent 配信。MongoDB。
- 検知境界: 検知（閾値発火・dedup）は Cloud Monitoring 等の上流の責務。本体は
  「発火済みアラート」を3系統の peer ingest で受ける:
  ① EC 業務イベント（RabbitMQ購読） ② Cloud Monitoring webhook ③ CI/Trivy の脆弱性検知。
- 分類: Classifier/Policy/Rule 3層。完全一致（既知・即時1秒・決定論）→
  類似（Elasticsearch or InMemory Jaccard・confidence付き「準・既知」）→ 未知。
- AI調査（未知のみ起動）: Google ADK による 7エージェント hub-and-spoke
  マルチエージェント（Coordinator / EvidenceCollector / RootCauseAnalyst /
  ImpactTriage / RemediationPlanner / RunbookEscalation / RemediationReviewer）。
  EvidenceCollector は read-only ツールで Cloud Logging・Terraform適用差分・
  GitHub実コミット&unified diff・過去類似インシデントDBを自律的に引く。
  自責/他責を判定して出口を「修正PR起案」と「運用エスカレーション草案」に振り分ける。
- モデル: Gemini 2.5 Pro（Vertex AI 経由・ADC認証）。単一Gemini経路とADK経路を
  ポート（AIInvestigationPort）の DI 差し替えで切替可能。
- 学習ループ: 人間の正解フィードバック → SimilarIncident 蓄積（類似分類の母集団）→
  閾値到達 or 手動で KnownErrorPattern に昇格 → 次回は1秒で既知分類（AI呼び出し不要）。
- リメディエーション: 調査=read / 修正=write を構造分離。脆弱性はGitHub Actions上で
  AIエージェントが実コード修正→Trivy再スキャン+テスト緑→draft PR（自動マージなし・人間承認ゲート）。
- 予兆ブリーフィング（今スプリントで実装）: 未来シグナル（未マージPR・未適用Terraform plan・
  負荷スケジュール）×過去インシデント記憶を Gemini が突合し、引用(citation)必須で
  リスク予報。引用は実在シグナルとの照合で検証し、偽引用は自動除外（ハルシネーション・ガード）。
  統計MLではなく「既知シグナルの LLM 突合推論」なのでデモ規模でも成立。
- フロントエンド: React ダーク観測コンソール。SSE でアラートがリアルタイム降着。
  証拠パネル（実ログ・実Terraform差分・実コミットdiffへのリンク）、承認/却下、
  承認済み一覧の Analytics ページ。
- デプロイ: Cloud Run（frontend/edge）+ Compute Engine（RabbitMQ常駐Subscriber）の折衷。
  トレードオフは ADR 化。Terraform で IaC 管理、GitHub Actions で CI/CD。

【DevOpsドッグフーディング（審査観点「実運用DevOps」への直接回答）】
このリポジトリ自身の CI/CD が本プロダクトの入力源になっている:
- app.yml: typecheck/UT/E2E → イメージbuild → Cloud Run/GCE デプロイ
- Trivy スキャン → 検出脆弱性を本番の /ingest/security-scan に送る（＝自分を監視する）
- ai-remediation.yml: repository_dispatch でAIが実コード修正→テストゲート→draft PR
- terraform.yml: plan/apply パイプライン
「監視対象のECも、監視するエージェント自身も、同じ DevOps ループの中にいる」

【デモシナリオ（7本+予兆）と正直さの原則】
1 決済タイムアウト（既知・実注文投入→1秒分類） 2 DBコネクション枯渇（未知→AI調査）
3 フィードバック学習→昇格（次回1秒） 4 インフラ障害（Cloud Monitoring実経路）
5 CVE脆弱性→AI調査→実修正draft PR（CI実経路と同一） 6 terraform apply起因障害（構造化差分が決定打）
7 アプリコード退行（実gitコミットの実diffをAIが読んで原因特定）
予兆: DB接続枯渇の予報（PR pool縮小×Terraform plan×週末セール負荷×過去同型N件、引用付き）
- 正直さ: 合成入力は UI 上で amber バッジ表示（「検知の入口のみ合成。変換→分類→AI調査は実経路」）。
  エンドポイントの無い偽ボタンは作らない。デモ卓に「実トリガ/クラウド実検知/合成入力」の
  リアルさバッジを常設。

【数字（事実）】
- テスト694件・110ファイル全緑 / 本番コード約2万行 / ADKエージェント7体
- 既知分類は約1秒・AI調査は数十秒〜（未知のみ起動＝コスト最適化）
- 検知dedup: dedupKey+occurrenceCount で同型アラート嵐を1件×Nに畳む

【書いてはいけないこと】
- 「本番トラフィックで運用中」等の運用実績の示唆（デモ環境である）
- 統計ML/時系列予測をやっているかのような表現（LLM推論+引用検証である）
- 未実装機能（イベントソーシング基盤等）を実装済みかのように書く（「設計済み・拡張点」とは書いてよい）
```

## §B 資料別プロンプト（§A のあとに1つずつ貼る）

### B-1 ProtoPedia「ストーリー」欄（課題・ユーザー・特徴）

```
ProtoPedia のストーリー欄を書いてください。構成は指定の3点:
①本作品で解決したい課題とその背景 ②想定する利用ユーザー ③プロダクトの特徴。
条件: 合計800〜1200字。①は「調査・評価・レビューの人手コスト」に焦点。
③は審査観点4つ（面白さ/必然性/自律性/実運用DevOps）に1つずつ対応する特徴を
見出し付きで。特徴の筆頭は予兆ブリーフィング（起きる前に引用付きで予報）。
ドッグフーディング（自分自身を監視するCI/CD）を必ず含める。
```

### B-2 ProtoPedia「概要」欄

```
ProtoPedia の概要欄を200〜300字で。1文目は「起きる前に引用付きで予報し、
起きた後は7体のAIエージェントが実ログ・実コミットdiffを横断して原因を特定する
AI-SRE エージェント」の趣旨で掴む。検知はしない（既存観測基盤の上に乗る）ことを
1文で明示。
```

### B-3 動画台本（3分・冒頭60秒が勝負）

```
提出動画の台本を作ってください。全体3分・以下の構成を厳守:
- 0:00-0:15 「本番でDBが落ちる"前"に、AIがこう言いました」→予報カード
  （HIGH・confidence・引用チップ3つ: PR pool縮小/週末セール負荷/過去同型3件）
- 0:15-0:35 引用チップをクリック→実在のPR・過去アラートに解決（根拠が本物・
  偽引用は検証で自動除外、と一言）
- 0:35-1:00 「では実際に起きたら？」→アラート降着(SSE)→未知と分類→
  ADK 7エージェントが自律調査を開始する画面
- 1:00-2:00 調査結果: 実コミットdiff引用の原因特定→影響トリアージ→
  修正draft PR（人間承認ゲート）。既知なら1秒で分類される対比も見せる
- 2:00-2:40 学習ループ（フィードバック→昇格→次回1秒）と
  ドッグフーディング（Trivy→自分自身にingest→AIが直すPR）
- 2:40-3:00 アーキの拡張性（検知の外置き・ポートDI・予兆の源は配列で追加可能）
各カットに「画面に映すもの」「ナレーション」「画面下テロップ」の3行を書く。
ナレーションは話し言葉・1カット20秒以内で読める分量。
```
