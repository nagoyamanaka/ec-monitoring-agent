### 1.7 相関の健全化＝ハルシネーション vs 関連（2026-07-04 判断・David/Lisa 直撃）

- **発見（実機）**: 決済タイムアウト（他責・外部決済サービス起因）のレポートが、同時発生した在庫アラートを根拠に「在庫競合→DB高負荷→決済タイムアウト」という**証拠のない因果を捏造**していた（＝「LLM は適当」を地で行く失点。放置すれば David/Lisa に刺さる）。
- **論点**: 相関は **精度 vs 再現率**の綱引き。締める（時間窓等の決定論フィルタ）と正当な相関（例: インフラ障害→アプリ500＝Cloud SQL 縮小の物語・現 3b→5）まで削れ、緩めると捏造が通る。**両立の鍵は「時間の近さ」でなく「共有証拠の有無＋因果の向きの妥当性」**。
- **判断**: ① 汚染源だった在庫競合デモ（旧3）を廃止＋シナリオ番号 -1 繰り上げ。② relatedAlerts の LLM 契約を厳格化（共有証拠必須・推測の因果橋禁止・他責の再分類禁止）を即時投入。③ 実効化の残タスク（案B=citation 必須化＋確信度ゲート／案A=相関検証エージェント）を **todo §J** に登録 → **案B（J1）・案A（J2）とも 2026-07-05 実装済み**（J1=citation の収集済み証拠 id 実在照合＋確信度加点ゲート／J2=correlation_verifier 批判役エージェント・既定 flash で D3 逼迫に配慮・7→8エージェント。詳細は todo §J1/J2）。実 Gemini での実走確認（正当相関が残ること・fallback 率非悪化）は人間タスク＝F8/D3 実走と同時。
- **なぜ審査に効くか**: 既存の「引用検証＝偽引用を実在照合で落とす」（§3.1 予兆）と**同型の答えを調査の相関にも出す**＝「ハルシネーション否定の可視化」を予兆と調査の両輪で一貫させる。審査観点「自律的判断の設計／実運用の堅牢性」（David）と「LLM は信用できるのか」の不安払拭（Lisa）に直撃。**人間なら取らない出鱈目な因果を、エージェントの役割（批判役）と証拠グラウンディングで機構的に排除した**という設計の物語になる。

## 3. 予兆スコープの意思決定：出すのは「1本、余れば2本目」

> 制約: せいぜい1〜2シナリオ。**質を1本に集中**し、2本目は同一機構の seed 替えに留める。

### 3.1 本命（P0）＝ DB接続枯渇の予報（フラッグシップ・これが60秒フック）

> ✅ **実装着地（2026-07-05・todo F1〜F8/F10〜F12）**: seed 3系統＋MEMORY 突合＋偽引用ドロップの E2E 固定＋🛡先手1行＋デモコンソールまで完了。残りは人間タスク＝実 Gemini 実走確認（tf apply 後）と録画テイク。

3つの未来シグナル＋記憶が**全部噛み合う唯一の代表シナリオ**。citation の説得力が最大。

```
根拠（引用）が3系統そろう:
 ├ GitHub open PR  … 「DB pool 100→40 縮小」（未マージ＝FUTURE_CHANGE）
 ├ Terraform plan  … 「connection 上限縮小」（未適用＝FUTURE_CHANGE）
 └ Schedule        … 「土20:00 セール→checkout 負荷x5」（SCHEDULE）
        ×
   記憶（MEMORY）  … 過去「pool縮小+高負荷→枯渇」N件（SimilarIncident.sourceAlertId で実在Alertに解決）
        ↓ Gemini（citations 必須・引用検証で偽引用を落とす）
   「土20:00、DB接続枯渇 HIGH（confidence 0.78）
    根拠: [PR#123 pool縮小] × [Sat 20:00 負荷x5] × [過去同型N件]」
```

- **これを60秒フックの開幕に置く**（§5）。「事後に賢く調べる」より「起きる前に引用付きで予報する」が掴みとして圧倒的。
- 引用検証（実在シグナル照合・偽引用ドロップ）を**画面で見せる**＝ハルシネーション否定の可視化＝Lisa/David の「LLMは適当」懸念への直接回答。

### 3.2 2本目（stretch・余力時のみ）＝ 同一機構で seed だけ替える

- 例: 「決済プロバイダの障害告知（PR/schedule 相当のシグナル）× 過去の決済タイムアウト記憶 → 決済失敗急増を予報」。
- **新規コードは書かない**（seed とプロンプト文脈のみ）。2本目は「同じ仕組みが別ドメインでも効く」汎用性の証明用。間に合わなければ即切り。

### 3.3 やらない

- 統計ML・時系列予測（データ量前提・レッドオーシャン。ADRで線引き＝`step4-1` §7.8）。
- stretchⅢ（event-log 基盤・`EventLogPrecursorSource`）＝ハッカソン後。設計/ADRのみ（`step4-1` §7.10）。継ぎ目 `ForecastSignalSource[]` だけ守る。

## 5. 開幕60秒の設計（D-1 × 予兆）

```
0-15秒  「本番でDBが落ちる"前"に、AIがこう言いました」→ 予報カード（HIGH・confidence・引用チップ3つ＋今打てる先手1行）を最初に見せる
15-35秒 「防ぐ手まで出ています」→ 先手（🛡）を読み、引用チップをクリック→ 実在の PR / plan / 過去Alert に解決（＝根拠が本物・偽引用は検証で落ちる・引用リンクが先手の実行先）
35-60秒 「もし先手を打たずに発火したら？」→ 反応的パイプライン（分類→ADK調査→承認）へ接続。防げなかった世界線も同じ証拠で受け止める＝予兆と調査が1ループで繋がる
```

掴みで「予知の驚き」→「防ぐ手の提示」を取り、続けて既存の実装厚（調査・学習ループ）を保険側の受け皿として回収する構成。Marcus の60秒とAlexのペイン、Davidの実装厚が1本の線に乗る。

> **UI 側の受け（F10-②/F11・2026-07-05 着地）**: 主役は各予報カード内の「🛡 今打てる先手」（F11a・AI が citations 接地で生成・実行主体は人間）。35-60秒の遷移フレーズは予兆ページ末尾の橋渡しCTA（`ForecastBridgeCta`・見出し「もし防ぎきれずに発火したら？」＝**保険トーン**）が画面側で受け、クリック1つで /alerts（反応的パイプライン）へ遷移できる。純ナビゲーション・write-zero 維持（実行ボタンの視覚語彙を持ち込まない）。台本もこの主従（防ぐが主・受けるが保険）に合わせて上記の通り更新済み。
