## 2. なぜ予兆が最優先レバーか（天井を上げる）

| 効く審査基準 | 効き方 |
| --- | --- |
| 基準1 自律性・必然性 | 「まだ起きていない障害」をエージェントが未来シグナル×記憶を突合して**自律予報**＝AIである必然性が最も濃い |
| 基準2 ストーリー | **reactive（事後）→ proactive（事前）** のシフトレフト。既存パイプラインの伏線回収で物語が一本化 |
| 基準4 体験・突き抜け | 「起きる前に、引用付きで教える」は既存 stretch（ADKの高度さ）と**直交する独自価値** |

**低リスクの根拠（実コードで確認済み）**:
- 予兆は**追加 read-only ハンドラ**（`ForecastRiskCommandHandler`）として横に生やすだけ。ランタイム本線（`AnalyzeAlert`/`InvestigateAlert`）は無傷（`step4-1` §7.5）。
- 既存資産を再利用: read-only Gateway 群（GitHub/Terraform）＋ `SimilarIncident`（`sourceAlertId` back-link で citation を実在 Alert に解決可能）。
- **録画前提でOK**（`step4-1` §7.6）。ライブ安定化コスト＝Davidの懸念を負わない。write ゼロ。
- `FORECAST_ENABLED` 既定 off＝本番非侵食。フロントのナビも off で隠れる（実装済みの土台）。

## 3. 予兆スコープの意思決定：出すのは「1本、余れば2本目」

> 制約: せいぜい1〜2シナリオ。**質を1本に集中**し、2本目は同一機構の seed 替えに留める。

### 3.1 本命（P0）＝ DB接続枯渇の予報（フラッグシップ・これが60秒フック）

3つの未来シグナル＋記憶が**全部噛み合う唯一の代表シナリオ**。citation の説得力が最大。

```
根拠（引用）が3系統そろう:
 ├ GitHub open PR  … 「DB pool 100→40 縮小」（未マージ＝FUTURE_CHANGE）
 ├ Terraform plan  … 「connection 上限縮小」（未適用＝FUTURE_CHANGE）
 └ Schedule        … 「土20:00 セール→checkout 負荷x5」（SCHEDULE）
        ×
   記憶（MEMORY）  … 過去「pool縮小+高負荷→枯渇」N件（SimilarIncident.sourceAlertId で実在Alertに解決）
        ↓ Gemini（citations 必須・引用検証で偽引用を落とす）
   「土20:00、DB接続枯渇 HIGH（confidence 0.78）
    根拠: [PR#123 pool縮小] × [Sat 20:00 負荷x5] × [過去同型N件]」
```

- **これを60秒フックの開幕に置く**（§5）。「事後に賢く調べる」より「起きる前に引用付きで予報する」が掴みとして圧倒的。
- 引用検証（実在シグナル照合・偽引用ドロップ）を**画面で見せる**＝ハルシネーション否定の可視化＝Lisa/David の「LLMは適当」懸念への直接回答。

### 3.2 2本目（stretch・余力時のみ）＝ 同一機構で seed だけ替える

- 例: 「決済プロバイダの障害告知（PR/schedule 相当のシグナル）× 過去の決済タイムアウト記憶 → 決済失敗急増を予報」。
- **新規コードは書かない**（seed とプロンプト文脈のみ）。2本目は「同じ仕組みが別ドメインでも効く」汎用性の証明用。間に合わなければ即切り。

### 3.3 やらない
- 統計ML・時系列予測（データ量前提・レッドオーシャン。ADRで線引き＝`step4-1` §7.8）。
- stretchⅢ（event-log 基盤・`EventLogPrecursorSource`）＝ハッカソン後。設計/ADRのみ（`step4-1` §7.10）。継ぎ目 `ForecastSignalSource[]` だけ守る。

## 5. 開幕60秒の設計（D-1 × 予兆）

```
0-15秒  「本番でDBが落ちる"前"に、AIがこう言いました」→ 予報カード（HIGH・confidence・引用チップ3つ）を最初に見せる
15-35秒 引用チップをクリック→ 実在の PR / plan / 過去Alert に解決（＝根拠が本物・偽引用は検証で落ちる）
35-60秒 「では実際に起きたら？」→ 反応的パイプライン（分類→ADK調査→承認）へ接続。予兆と調査が1ループで繋がる
```
掴みで「予知の驚き」を取り、続けて既存の実装厚（調査・学習ループ）を回収する構成。Marcus の60秒とAlexのペイン、Davidの実装厚が1本の線に乗る。

## 6. 進め方とガードレール

```
main は常時 全テスト緑（7/2時点 694）・提出可能を維持
  └ feature/forecast ブランチで予兆を実装（録画前提・FORECAST_ENABLED off で本番非侵食）
      ├ P0: §3.1 DB枯渇予報 1本を録画品質まで（todo F系 参照）
      ├ 余力: §3.2 2本目 seed 替え / §4 D-2,D-3
      └ 間に合わなければ「設計＋ADRで語る」に退避（step4-1 §7 が逃げ道）
D-1(60秒フック)/D-2/D-3 は予兆の録画テイクと同時に詰める
```

- **停止条件**: 締切2日前（7/8）時点で予兆P0が録画に届かなければ、予兆は設計/ADR提示に切替え、残りをデモ防御に全振り。
- **不変原則の維持**: 予兆も「調査=read / write隔離 / 引用検証」を越境しない。`ForecastSignalSource[]` の継ぎ目（`step4-1` §7.9）を守り stretchⅢ の伏線を残す＝拡張性の実証として発表でも使う。
