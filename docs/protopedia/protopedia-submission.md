## タイトル

**Kizashi（兆し）— 起きる前に予報し、起きた後は自律調査する AI-SRE エージェント**

---

## 概要（100字以内・95字）

障害アラートの“後”の原因調査・報告をAIエージェントが肩代わり。人の承認で学習し、既知の障害は1秒で判定。起きる前のリスクも根拠付きで予報する、既存監視の上に乗るAI-SREエージェント。

作ったのは、既存の監視の**上に乗る**「アラート後工程の自動化パイプライン」と、その手前に置いた「予報」です。検知そのものは作っていません（Cloud Monitoring などの既存基盤の仕事のまま）。図の①〜⑥に沿って補足します。

### 1. 受け取る — 3系統の ingest

アラートの入口は 3 つ（① 業務イベントを RabbitMQ で購読 ② Cloud Monitoring の webhook ③ CI の Trivy スキャン結果の POST）。どれも同じパイプラインに合流します。同じ障害が連発したら 1 件×N 回に畳んで、アラートの嵐で画面が埋まらないようにしています。

### 2. 分類する — 既知は1秒、AI を呼ばない（→ 特徴3）

まず過去に確定したパターンと突き合わせ、完全一致なら **1 秒未満・決定論・AI コストゼロ**で確定。似ている事例があれば confidence 付きの「準・既知」。どちらでもない**未知だけ**が次の AI 調査へ進みます。重い LLM 呼び出しを未知に限定する＝コストを構造で抑える設計です。

### 3. 調べる — Google ADK の 8 エージェント（→ 特徴2）

未知アラートは Gemini 2.5 Pro（Vertex AI）＋ Google ADK のマルチエージェントが調査します。まとめ役（Coordinator）の下に、証拠収集・原因分析・影響評価・相関の検証（批判役）・修正方針・エスカレーション・PR レビューの役割を分担。証拠収集はすべて **read-only のツール**経由で、Cloud Logging の実ログ・Terraform の適用差分・GitHub の実コミット diff・過去事例 DB を横断します。

実行イベントは SSE で UI にライブ中継され、「いま何を調べているか」が見えます。AI が失敗しても集めた証拠リンクは残し、ワンクリックで再調査できます。

【画像②: AI 調査のライブ画面（調査タイムライン）】

### 4. 人が確かめ、システムが覚える — 学習ループ（→ 特徴3）

調査レポートは人間がレビューします。**承認**（訂正メモつき）すると解決済み事例として蓄積され、同型の再発はその訂正を根拠に即分類。頻出パターンは既知へ**昇格**（自動閾値 or ワンクリック）し、次回は 1 秒。**却下**すれば訂正の指摘つきで再調査させられます。この「未知→調査→承認→昇格→再発は 1 秒」の一巡は E2E テストで自動検証しています。

【画像③: 証拠パネルと承認 UI（実ログ・実 diff への根拠リンク）】

### 5. 起きる前に言う — 予兆ブリーフィング（→ 特徴1）

パイプラインの手前に「予報」を置きました。未来シグナル 3 種（未マージ PR／未適用の Terraform plan／週末セール等の負荷予定）と過去の障害の記憶を Gemini が突合し、「土 20:00、DB 接続枯渇 HIGH」のようにリスクを予報します。**返ってきた予報の引用は実在するシグナルと照合し、偽の引用は破棄・根拠ゼロのリスクは丸ごと破棄**。予報は事前生成してキャッシュ配信するので、閲覧のたびに AI 課金は発生しません。

【画像④: 予報カード（リスク・根拠の引用チップ・今打てる先手）】

### 6. 直すときは隔離する — write 分離とドッグフーディング（→ 特徴4）

調査は read-only、修正は GitHub Actions 上に隔離。脆弱性は AI が実コードを修正し、Trivy 再スキャン＋テストが緑になったら **draft PR**（自動マージなし・人間承認）——この自己修復パイプライン（`ai-remediation.yml`）は実装済みで、デモでは同じパイプラインが事前に起票した**実 draft PR** を提示します。しかもこの検知経路の入力は、**このリポジトリ自身の CI（Trivy）**が同じ `/ingest` に流し込む脆弱性です——監視対象も監視するエージェント自身も、同じ DevOps ループの中にいます。

【画像⑤: AI が起こした draft PR（テストゲート通過後）】

### どう作ったか（開発プロセス）

- **コード**: TypeScript のモノレポ。DDD + Clean Architecture で、AI 呼び出しはポート（interface）化 → 単一 Gemini 経路と ADK 経路を DI で差し替え、テストでは決定的スタブに差し替え。
- **テスト**: ユニット 1017 件＋実スタック E2E 22 件（すべて自動・全緑）。「承認→昇格→再発は1秒」の学習一巡や「偽引用の破棄」まで E2E で検証。
- **インフラ**: Terraform で IaC 化し、GitHub Actions から plan/apply（承認ゲート付き）。デプロイは Cloud Run（フロント/エッジ）＋ Compute Engine（RabbitMQ 常駐系）の折衷。
- **CI/CD**: push → typecheck/テスト → イメージビルド → デプロイ。この CI の Trivy スキャンがそのまま 6. の検知入力になっています。

さらに詳しい図と設計判断はリポジトリの `docs/architecture.md` にまとめています（公開後は GitHub の URL をここに貼る）。

## ストーリー

### ① 本作品で解決したい課題とその背景

障害対応で一番時間を食うのは「検知」ではなく、アラートが鳴った**後**です。ログ・コード履歴・インフラ変更を人手で行き来して原因を突き止め、影響を見積もり、報告を書く——しかも多くの現場では、同じ障害が再発しても毎回ゼロから調べ直しになります。この「調査・評価・報告」の後工程の負担を減らしたくて作りました。

### ② 想定する利用ユーザー

Web サービスを少人数で運用している SRE・オンコール担当・運用チーム。いまの監視基盤はそのままに、アラート後の調査だけ楽にしたい人（デモの監視対象は EC ですが、取り込み経路は汎用でドメインを問いません）。

### ③ プロダクトの特徴

**1. 起きる前に、根拠付きで予報する**
未マージ PR・未適用の Terraform plan・週末セールなどの負荷予定と、過去の障害の記憶を Gemini が突合し、「土 20:00、DB 接続枯渇 HIGH」のようにリスクを予報します。根拠の引用は実在するシグナルと照合して検証し、偽の引用は自動で落とします＝「LLM は適当なことを言う」への直接の対策を画面で見せます。

**2. 未知の障害だけ、8 エージェントが自律調査**
既知・類似は AI を呼ばず即確定。未知だけ Google ADK の 8 エージェント（証拠収集・原因分析・影響評価・相関の検証役など）が実ログ・実コミット diff・インフラ差分を read-only で横断し、根拠リンク付きのレポートを作ります。調査の実行過程は SSE でライブ中継され、「いま何を調べているか」が画面で見えます。

**3. 使うほど速く・安くなる学習ループ**
障害が人の承認によって学習され、同じ障害は次から類似・既知として即判定。頻出パターンは既知へ昇格し、以降は 1 秒・AI コストゼロ。却下すれば訂正の指摘つきで再調査させられます。「未知→調査→承認→昇格→再発は 1 秒」の一巡は E2E テストで担保済みです。

**4. 自分自身を監視するドッグフーディング**
このリポジトリ自身の CI（Trivy）が見つけた脆弱性を自分の検知パイプライン（`/ingest`）に流し、AI が自分のコードを修正して draft PR を起票する自己修復ループを実装しました（自動マージなし・人間承認）。デモでは同じパイプラインが事前起票した実 draft PR を提示します。監視対象も、監視するエージェント自身も、同じ DevOps ループの中にいます。

---

**正直さの原則**: デモの合成入力は UI 上のバッジで明示（入口のみ合成・分類→AI 調査は実経路）。修正 PR はライブ起票でなく、同じ AI 修正パイプラインで事前に起票した**実 draft PR** を提示します（書き込みトークン運用と PR 増殖回避のため）。数値は実測のみ（ユニットテスト 1017 件全緑・既知分類は約 1 秒未満・未知の AI 調査は約 2 分前後）。
